# TwoTower (loopback): Last.fm 1K и MovieLens-100k

Практика по дисциплине «Рекомендательные системы»: взять опубликованный алгоритм, воспроизвести его результаты на демонстрационном датасете авторов, обучить на принципиально другом датасете и сравнить метрики с заявленными.

| | |
|---|---|
| Алгоритм | TwoTower — [DanielRegaladoCardoso/loopback-twotower](https://huggingface.co/DanielRegaladoCardoso/loopback-twotower) |
| Демонстрационный датасет | [lastfm-1k-twotower](https://huggingface.co/datasets/DanielRegaladoCardoso/lastfm-1k-twotower): прослушивания музыки, 992 пользователя, 1.5 млн треков, 19 млн событий |
| Другой датасет | [movielens-100k](https://huggingface.co/datasets/DukeNLPGroup/movielens-100k): оценки фильмов, 943 пользователя, 1682 фильма, 100 тыс. оценок |

## Быстрый старт

```bash
bash scripts/predict.sh            # веса + датасет → вероятности следующего фильма, MovieLens-100k
WEIGHTS=weights/twotower_ml100k_logq.pt bash scripts/predict.sh   # то же на весах модели с logQ
bash scripts/predict.sh lastfm 2   # то же для Last.fm 1K на весах авторов (скачает около 620 МБ)
bash scripts/run_all.sh            # всё исследование: Last.fm → MovieLens → отчёт
```

Скрипты сами создают venv, ставят зависимости и скачивают данные и веса с Hugging Face. Нужны bash, curl и Python 3.10–3.13.

В Google Colab: открыть [notebooks/twotower_colab.ipynb](https://colab.research.google.com/github/Sandrolek/rec_sys/blob/main/notebooks/twotower_colab.ipynb), включить T4 GPU и выполнить все ячейки. Ноутбук клонирует репозиторий и запускает те же bash-скрипты.

## Результаты

Всё посчитано в Google Colab на T4: весь ноутбук занял около 15 минут, эпоха на Last.fm — 1.8 минуты. Полный отчёт — [results/REPORT.md](results/REPORT.md), метрики каждого запуска — `results/*.json`.

### Итог

**Воспроизвести удалось, но авторы себя перехвалили.**

- Их числа воспроизводятся почти до третьего знака: и на опубликованных весах, и при обучении с нуля.
- Но «Recall@K» у них на самом деле HitRate@K — доля пользователей, у которых в топ-K попал хотя бы один новый трек.
- Сравнивают они его со случайным *recall* (6.7e-6), а не со случайным hit rate (3.4e-3). Отсюда выигрыш «в 10 тысяч раз» вместо настоящих 21 раза.
- Бейзлайн «популярное» в их же протоколе лучше модели в три раза.
- На MovieLens-100k алгоритм в том виде, как его опубликовали, тоже проигрывает популярному. Обходит его только с поправкой logQ, которой у авторов нет.

### Last.fm 1K: протокол авторов

Кода оценки у авторов нет, поэтому их веса оценены примерно в двухстах вариантах протокола. Один совпал с заявленными числами с точностью до 0.4%:

- метрика — HitRate@K;
- оценивается тестовый период, из выдачи убраны только треки из train (прослушанные в val остаются);
- считаются только пользователи с историей в train: 844 против заявленных 847;
- исполнитель известен только у треков из train, у остальных подставляется исполнитель с индексом 0. Так сделано в демо авторов (`app.py` в их HF Space).

| HitRate@K | @10 | @50 | @100 |
|---|---|---|---|
| Заявлено авторами | 0.0708 | 0.2172 | 0.3140 |
| Веса авторов, наша оценка | 0.0711 | 0.2180 | 0.3152 |
| Обучение с нуля, наш запуск | 0.0818 | 0.2251 | 0.3104 |
| Бейзлайн: популярное | 0.2062 | 0.3709 | 0.4443 |
| Бейзлайн: случайная выдача | 0.0034 | 0.0166 | 0.0324 |

Loss в конце нашего обучения — 5.49, у авторов — 5.6.

### Last.fm 1K: те же веса в обычных метриках

| | HitRate@10 | HitRate@100 | Recall@10 | Recall@100 |
|---|---|---|---|---|
| Веса авторов, протокол авторов | 0.0711 | 0.3152 | 0.0002 | 0.0017 |
| Веса авторов, исполнитель известен у всех треков | 0.2713 | 0.4810 | 0.0019 | 0.0097 |
| Бейзлайн: популярное | 0.2062 | 0.4443 | 0.0006 | 0.0070 |
| Бейзлайн: случайная выдача | 0.0034 | 0.0324 | 0.000007 | 0.000067 |

Recall здесь — доля новых треков пользователя в тестовом периоде, попавших в топ-K.

- **Настоящий recall на два порядка ниже заявленного.** В тесте у пользователя в среднем около двух тысяч прослушиваний, и топ-100 находит около 1% его новых треков.
- **Ошибка в оценке авторов работает против них самих.** Многие треки теста не встречались в train. Их эмбеддинг не обучен, и модель узнаёт их только по исполнителю, а авторы подставляют им чужого исполнителя. Если взять настоящего исполнителя (он известен из каталога, утечки здесь нет), те же веса обгоняют популярное: HitRate@10 0.27 против 0.21.

### MovieLens-100k

Тот же алгоритм на оценках фильмов: 943 пользователя, 1682 фильма. Вместо исполнителя группой объекта служит набор жанров фильма.

Recall@K в тестовом периоде, из выдачи убрано всё, что пользователь видел раньше. Сплит `user` — по времени внутри истории каждого пользователя, история в train есть у всех 943:

| Recall@K | @10 | @50 | @100 |
|---|---|---|---|
| Гиперпараметры авторов (3 эпохи, батч 4096) | 0.0118 | 0.0485 | 0.0848 |
| Подбор по val: батч 4096, эпоха 24 | 0.0419 | 0.1739 | 0.2922 |
| То же с поправкой logQ, которой нет у авторов | 0.0870 | 0.3164 | 0.4769 |
| Бейзлайн: популярное | 0.0601 | 0.1834 | 0.2982 |
| Бейзлайн: случайная выдача | 0.0063 | 0.0316 | 0.0633 |

Сплит `global` — общая временная шкала, как у авторов; в тесте 166 пользователей, у 97 из них нет ни одного события в train:

| Recall@K | @10 | @50 | @100 |
|---|---|---|---|
| Гиперпараметры авторов (3 эпохи, батч 4096) | 0.0144 | 0.0546 | 0.0933 |
| Подбор по val: батч 4096, эпоха 6 | 0.0247 | 0.0791 | 0.1420 |
| То же с поправкой logQ, которой нет у авторов | 0.0769 | 0.2054 | 0.2929 |
| Бейзлайн: популярное | 0.0615 | 0.1978 | 0.3134 |
| Бейзлайн: случайная выдача | 0.0063 | 0.0316 | 0.0633 |

В протоколе авторов (HitRate@K) выводы те же, таблицы — в [results/REPORT.md](results/REPORT.md).

- **Гиперпараметры авторов не переносятся.** 3 эпохи с батчем 4096 на 80 тыс. событий — это 60 шагов градиента, модель почти не отличается от случайной выдачи.
- **После подбора батча и числа эпох алгоритм всё равно проигрывает популярному**: Recall@10 0.042 против 0.060 на сплите `user`.
- **Причина в функции потерь.** Негативы берутся из батча, популярные фильмы попадают туда чаще и получают заниженные оценки. Поправка logQ вычитает из оценки логарифм популярности, и с ней та же архитектура обходит популярное: 0.087 против 0.060.
- **Временной сплит авторов упирается в холодный старт.** Вектор пользователя — эмбеддинг по ID, для нового пользователя он не обучен. На MovieLens-100k при общем временном сплите новые 97 из 166 тестовых пользователей; на Last.fm 1K — 72 из 916, и авторы их просто не считают.

## Как устроено исследование

**Алгоритм.** Две башни: пользователь (эмбеддинг ID → MLP) и объект (эмбеддинги ID и группы → MLP), выходы нормируются, оценка — скалярное произведение с обучаемой температурой. Обучение — симметричный InfoNCE с негативами из батча, AdamW. Код архитектуры перенесён из HF Space авторов без изменений, поэтому их чекпойнт загружается как есть.

**Воспроизведение на Last.fm 1K** идёт в два шага: оценка опубликованных весов авторов и обучение с нуля с их гиперпараметрами (3 эпохи, батч 4096, lr 1e-3, weight decay 1e-5).

**Протокол оценки.** Репозиторий авторов на GitHub недоступен (404), кода оценки нет, а описание — одна строка: Recall@K на 847 отложенных пользователях с фильтрацией прослушанных треков. Если новых треков у пользователя сотни, обычный recall при K = 100 дать 0.31 не может. Поэтому каждая модель оценивается сразу в нескольких вариантах:

- какой период оценивается (test или val) и что считается уже виденным (train, train + val, ничего);
- пять определений метрики: `recall`, `hit` (хотя бы одно попадание), `recall_capped`, `event` (доля событий) и `first` (следующий новый объект);
- все пользователи или только те, у кого есть история в train;
- на Last.fm ещё и способ получить вектор пользователя: башня пользователя (исполнитель трека берётся из всех данных или только из train) либо среднее векторов его треков, как в демо авторов.

Отчёт находит вариант, ближайший к заявленным числам, и дальше сравнивает всё в нём. Для Last.fm он нашёлся с точностью 0.4% (см. выше).

**MovieLens-100k.** Каждая оценка считается взаимодействием «посмотрел фильм». Вместо исполнителя группой объекта служит набор жанров фильма. Архитектура, функция потерь, lr и weight decay не меняются; по val подбираются только размер батча и число эпох.

**Бейзлайны.** Случайная выдача (точные формулы) и топ популярного по числу пользователей в train. Каталоги отличаются на три порядка, поэтому датасеты сравниваются по отношению метрики к бейзлайну, а не по самим значениям.

## Скрипты

| Скрипт | Что делает |
|---|---|
| `scripts/predict.sh [movielens\|lastfm] [N]` | Ставит окружение, скачивает веса и данные, берёт N пользователей из test и печатает вероятности следующего объекта |
| `scripts/reproduce_lastfm.sh [all\|eval\|train]` | Оценивает веса авторов на Last.fm 1K и обучает модель с нуля |
| `scripts/train_movielens.sh` | Обучает модель на MovieLens-100k: оба сплита, гиперпараметры авторов, подбор батча, logQ |
| `scripts/run_all.sh` | Запускает всё подряд и собирает отчёт |
| `scripts/download.sh ЦЕЛЬ...` | Скачивает датасеты и веса через curl |
| `scripts/env.sh` | Создаёт venv и ставит зависимости; подключается из остальных скриптов |

Переменные окружения: `PYTHON=python3.12` — каким интерпретатором создавать venv, `USE_SYSTEM_PYTHON=1` — работать без venv, `WEIGHTS=путь` — свои веса для `predict.sh`.

## Структура

```
twotower/model.py      архитектура авторов, функция потерь, сохранение и загрузка весов
twotower/data.py       Last.fm 1K и MovieLens-100k в общем формате
twotower/train.py      обучение
twotower/evaluate.py   top-K по всему каталогу, варианты протокола, бейзлайны
twotower/predict.py    вероятности следующего объекта
twotower/report.py     сводный отчёт results/REPORT.md
scripts/               bash-скрипты
notebooks/             ноутбук для Google Colab
weights/               веса двух моделей для MovieLens-100k: алгоритм авторов и он же с logQ (по 1.2 МБ)
results/               метрики всех запусков и отчёт
```

## Ресурсы

Бесплатного Colab с T4 хватает: весь ноутбук выполняется примерно за 15 минут. Модель для Last.fm — 107 млн параметров (430 МБ), почти все в эмбеддингах треков; данные — 15.3 млн событий; эпоха на T4 — 1.8 минуты. MovieLens-100k можно считать и на CPU, около 9 минут.
